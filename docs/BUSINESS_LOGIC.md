# Бизнес-правила BidStage

## Шара (обязательное правило)

**Каждая ставка должна сопровождаться публичным постом со ссылкой на лот в одной из поддерживаемых соцсетей.**

### Поддерживаемые домены

`vk.com`, `m.vk.com`, `facebook.com`, `m.facebook.com`, `web.facebook.com`, `fb.com`, `twitter.com`, `x.com`, `mobile.twitter.com`, `t.me`, `telegram.me`, `ok.ru`, `m.ok.ru`, `instagram.com`, `linkedin.com`, `reddit.com`, `pinterest.com`.

### Как проверяется

1. **При подаче ставки** (синхронно): только домен по белому списку и валидный URL.
2. **Через ~60 секунд** (асинхронно): GET-запрос на сам пост, поиск подстроки `/lot/<id>` в HTML.
   - Найдено → `share_verified=TRUE`, ставка участвует в торгах
   - Не найдено / 404 / удалили пост → ставка отклоняется
   - Ретраи: 1с / 5с / 30с при 429/502/503/504 или сетевой ошибке

### Что не проверяется

- Что пост действительно опубликовал именно этот пользователь (нет привязки к аккаунту соцсети)
- Что в посте нет накрутки

В dev-режиме `VK_AUTO_VERIFY=1` шара принимается без HTTP-проверки.

## Антиснайпинг

Если ставка сделана в **последние 180 секунд** до конца торгов:

- Таймер автоматически продлевается на 180 секунд
- Все смотрящие лот получают WebSocket `timer_extended`
- В `lot_events` записывается событие `timer_extended`

Реализация: `routes.py:_execute_bid_transaction`

```python
secs_left = (end_time - now).total_seconds()
extended = False
if 0 < secs_left < 180:
    new_end_time = now + timedelta(seconds=180)
    models.update_lot_end_time(conn, lot_id, new_end_time)
    extended = True
```

Это значит: невозможно «перехватить» лот ставкой за секунду до конца — у других участников всегда будет минимум 3 минуты на ответ.

## Прокси-ставки (автоматическая перебивка)

Альтернативный режим в модалке ставки. Указывается **максимум**, и система:

- При новой ставке другого юзера — автоматически делает встречную ставку на минимально необходимый шаг
- Останавливается, если кто-то поставит больше вашего максимума
- Не разглашает максимум другим участникам

Хранится в таблице `proxy_bids` (одна активная запись на (lot_id, user_id)).

Реализация: `payments.try_proxy_rebid` вызывается в момент `_accept_bid` для другого юзера.

Шара публикуется один раз — она применяется ко всему диапазону прокси-ставок.

## Каскад платежей

После завершения лота победитель имеет 24 часа на оплату. Если не оплатил:

```
1. Payment.status = 'cancelled'
2. Эскроу-сумма возвращается на баланс победителя
3. Найти следующего биддера: ORDER BY amount_usd DESC, id ASC
4. Если есть — создать ему новый payment, уведомление
5. Если каскад исчерпан → lot.status = 'cancelled' → автоматический relist через 24 часа
```

Шедулер `payments.cascade_expired_payments` запускается каждые 30 секунд и проверяет все `payments` со статусом `awaiting_payment` старше 24 часов.

## Эскроу

### Жизненный цикл денег

```
1. balance.deposit (пополнение картой) → user.balance_usd += amount
2. bid.placed                          → user.balance_usd -= amount (заморозка)
3. outbid                              → user.balance_usd += amount (разморозка)
4. lot.won + payment.paid              → платформа удерживает деньги
   payment.held_in_escrow = TRUE
5. seller отправил билет               → ticket_delivered = TRUE
6. buyer подтвердил получение          → buyer_confirmed = TRUE
7. payment.released_to_seller = TRUE   → seller.balance_usd += amount * (1 - 10%)
                                          платформа удерживает 10% комиссии
```

### При спорах

Если покупатель не подтвердил, но и не опровергает — деньги остаются в эскроу до решения вручную через `bidstage_support` (бот в чате).

## Тарифы и комиссии

| Действие | Сумма |
|---|---|
| Листинг (создание лота) | $5 (списывается с баланса при публикации) |
| Featured (карусель «Топ») | +$10 опционально |
| Комиссия с продажи | 10% |

Если лот не продаётся — листинг не возвращается, но 10% не списывается.

## OTP при ставке

Каждая ставка требует одноразового кода (если `BID_OTP_DISABLED != 1`):

1. Пользователь жмёт «Сделать ставку», вводит сумму и URL
2. Запрос на OTP → создаётся `otp_codes` запись (6 цифр, 5 минут)
3. Код приходит как уведомление в шапке (колокольчик)
4. Пользователь вводит код → `consume_otp_code` помечает использованным
5. Ставка проходит

Защита: одна и та же сумма + URL не пройдёт повторно с тем же кодом.

## Дедуп ставок и уведомлений

### Ставки

`models.duplicate_bid_exists(lot_id, user_id, amount, share_url)` — нельзя сделать вторую ставку на ту же сумму с тем же URL подряд от того же юзера. Защита от двойного клика.

### Уведомления

`notify.insert_notification` не создаёт уведомление с тем же `(user_id, kind, lot_id)` если уже есть **непрочитанное** за последний час. Защита от шедулерных дублей.

## Категории лотов

`lot_type`:
- `tickets` — концерты, шоу, мероприятия
- `vip` — VIP-пропуски, бэкстейдж
- `table` — рестораны, столики
- `concert` — синоним `tickets` (легаси)

Категории отображаются как табы в каталоге. Также `hot` — это виртуальная категория «end_offset_seconds < 3600 AND status = 'active'».

---

## Статусы лотов

```
upcoming  — ещё не начался (start_time > NOW())
active    — идут торги (NOW() < end_time)
ended     — завершён, есть/нет winner
cancelled — отменён (например, исчерпан каскад)
```

---

## Статусы платежей

```
pending           — payment создан, не оплачен
awaiting_payment  — синоним pending (легаси)
paid              — оплачен (деньги в эскроу)
cancelled         — отменён (каскад или ручная отмена)
released          — деньги перечислены продавцу
disputed          — спор (зависает в эскроу)
```

| `chat_message` | Сообщение в чате | получателю |

## Темплейты бот-сообщений

Бот `bidstage_support` шлёт сообщения в чат лота при ключевых событиях:
- Победа: «Поздравляем! Вы выиграли лот за $X. У вас 24 часа на оплату»
- Не оплачено: «Срок оплаты истёк»
- Каскад: «Лот переходит к вам! Сумма к оплате: $X»

Сообщения формируются в `notify.notify_event(send_chat=True)`.
